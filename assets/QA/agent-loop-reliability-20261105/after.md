## New regressions and still-open failures

Cause hypotheses are inferred from run events and code reading; none was confirmed by changing code.

1. **S15 — firm false success (open, target miss).** The run's obligation list contains only `presentation:map`; `ObligationKind` in `app/server/domain/agent/capability_route.py:30` is `location | data | analysis | presentation`, and nothing types "identify what place these coordinates are" (the resolver only echoes `Resolved 46.0037, 8.9511.` with no reverse-geocode requirement). The WS2 completion summary therefore reports a fulfilled request. Likely fix area: route/obligation extraction (an identification/answer-text obligation) plus a reverse-geocode requirement in `OBLIGATION_REQUIREMENTS`.
2. **S10-T2 — regression: cost and presentation contract.** (a) 140k tokens / 10 calls / 3 `no_progress` decisions, twice the baseline. (b) Render attempts 1 and 2 were both marked `failed`; the answer cites "requested places outside the map view: World". `PresentationContract.view_findings` (`app/server/domain/agent/presentation_contract.py:50-76`) tests each target's centre point against the viewport; a global-scope target ("World") has an arbitrary centre that a view fitted to three events need not contain, so the check fails regardless of what is rendered. Attempt 2 also reported 9 rendered features for a 3-event layer (stale 30-day features still present), so the replace-vs-add behaviour of the second plan also needs a look. Result: the map never shows the 24 h set.
3. **S10-T1 — answer contradicts the map (partial false claim) and silent truncation.** The model prose says the map shows all 205 events; only 25 are on the map (`transform_evidence` derived 25 records, as in the baseline). The grounded footer ("only 25 of 205") is correct but sits beside the false sentence, so model-authored claims are still not checked against the completion summary. Also one invalid call: `apply_map_plan` semantic validation before the retry.
4. **S13 — dead-end exploration still unbounded (open).** Unrelated `IMERG_Precipitation_Rate` fetch, `transform_evidence` on a raster, 14 calls / 57 s / 122k tokens before an honest "not completed". WS4 validates arguments against manifests but does not prune capabilities unrelated to the requested phenomenon (fire) or stop after "raster descriptor has no numeric records". Area: capability selection/budget in the native loop and `transform_evidence` raster rejection recovery.
5. **S03 / S06 — over-eager place disambiguation (open).** Brandenburg Gate (landmark with a clear top candidate) and Wellington (NZ vs Texas) still end in a clarification question. Area: resolver ambiguity policy (candidate ranking/importance threshold) in `resolve_geospatial_location`. S06 remains a scenario-design problem as well (see baseline).
6. **S16 — radar unavailable path (open).** T1 returns the raw coverage-policy string and offers no nearest alternative layer; T2 now asks which place to show although Tokyo was resolved in T1 and the user said "just show Tokyo" (the ledger carries the failed T1 task but the "show Tokyo" intent is classified as a clarification). Area: WS3 task ledger/`compatible_tasks` and the policy-rejection formatting in the answer grounding.
7. **S08-T2 token cost (regression, minor).** The same question that the baseline answered with one `inspect_evidence` (18.8k tokens) now runs `transform_evidence` + `inspect_evidence` (45.4k tokens, 5 calls). Correct and no provider call, but the evidence-reuse path is more expensive.
8. **Environment: 429 rate 28%** (10 of 36 runs), clustered, not agent-loop logic. Every affected scenario was re-run to a clean result; S12-T1 needed five attempts.
